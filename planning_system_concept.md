## 1. Контекст и границы

**Продукт**: чат-платформа РоботМия (B2B SaaS для коммуникаций).

**Команда**: 1–3 разработчика. Пользователь системы — продакт-овнер (изначально один), позже частичный read-only доступ для руководства.

**Главная боль**: сложно держать связь между годовой целью и ежедневной задачей.

**Три закрываемые боли** (приоритет MVP):
- B. «Не помню, какие задачи в Kaiten двигают цели, а какие — суета».
- C. «Каждый понедельник трачу час, чтобы понять, что было сделано на прошлой неделе и что важно на этой».
- D. «Не вижу, какие сделки тормозит наша разработка».

**Источники данных**:

| Система | Что хранит | Статус интеграции |
|---|---|---|
| Kaiten | Задачи разработки | Двусторонняя синхронизация уже есть |
| Grafana | Технические метрики | Webhook + cron pull |
| Second Brain (своя БД) | Клиенты, сделки, воронка, не-разработческие задачи | Нативные joins |
| Product Analytics | Продуктовая аналитика | Заглушка-сущность |

## 3. Объектная модель

### 3.1. Иерархия

```
Направление (Domain)
 ├─ year_focus: text                           ← одна фраза-фокус года (поле, не сущность)
 │
 ├─ Метрики (3 типа: Числовая / Бизнес / Выполнение)
 │   ├─ source: kaiten / grafana / second_brain / product_analytics / manual
 │   └─ Цели по горизонтам (год/квартал/месяц/неделя)
 │
 ├─ Инициативы (4 типа + авто «Поддержка»)
 │   ├─ due_period_id ──▶ Период (неделя)
 │   ├─ RICE-поля (приоритизация)
 │   ├─ Ключевые допущения
 │   ├─ Kill criteria
 │   ├─ Зависимости от других инициатив
 │   ├─ Связанные клиенты (повлияет на)
 │   └─ Эксп.-поля (для типа «Эксперимент»)
 │
 ├─ Периоды (год / квартал / месяц / неделя)
 │   ├─ Снимок целей метрик
 │   ├─ Запланированные инициативы и задачи
 │   ├─ Доступное время (capacity_hours)
 │   └─ Структурированная ретроспектива (4 поля)
 │
 ├─ Сделки
 │   ├─ Этапы: лид / пилот / прод / отвалившийся
 │   ├─ Дефолтная длительность пилота (на сделку)
 │   ├─ Контракт: минимум + ожидаемый факт
 │   └─ Платежи (отдельная таблица; рекуррентные авто-создаются)
 │
 └─ Задачи (Kaiten для разработки, Second Brain для остального)
     └─ planned_date — задача на конкретный день (не блок дня)
```

### 3.2. Сквозной пример

**Направление**: «Робот Мия».
**Фокус года 2026**: «Платформа становится зрелой и выходит на устойчивую выручку».

**Метрики 2026**:
1. **Выручка** (Бизнес) — 20 000 000 ₽.
2. **Подписания** (Бизнес) — 40 новых клиентов.
3. **Критический функционал** (Выполнение) — SDK / Email / Аналитика 2.0 / Конструктор.
4. **Скорость обработки вебхуков** (Числовая) — p99 < 200ms (старт 250).
5. **Пропускная способность API** (Числовая) — N rps.
6. **Критические баги** (Числовая) — 0 / квартал.

### 3.4. Инициатива

**4 типа** + 1 авто:

| Тип | Когда |
|---|---|
| **Блокер клиента** | Без этого пилот/прод не пойдёт у конкретных сделок |
| **Зрелость продукта** | Базовая надёжность, паритет |
| **Тех. долг** | Рефакторинг, гигиена |
| **Эксперимент** | Гипотеза (обязательны эксп.-поля §3.4.2) |
| **(авто) Поддержка** | Раз в квартал |

#### 3.4.1. Базовые поля Инициативы

| Поле | Обязательно | Зачем |
|---|---|---|
| `title` | Да | — |
| `type` | Да | См. таблицу |
| `description` | Опц. | Контекст конкурентов, доказательства, ссылки |
| `jtbd` | Только для блокеров и зрелости | Работа клиента |
| `linked_metric_ids` | Да (≥1) | Связь к метрике |
| `linked_deal_ids` | Только для блокеров | Многие-ко-многим, какие сделки разблокирует |
| `linked_client_ids` | Опц. | Существующие клиенты (стадия договора и т.п.), на которых повлияет — см. §3.4.3 |
| `due_period_id` | Да | Неделя |
| `estimate_hours` | Да (для RICE) | См. §3.4.3 |
| `key_assumptions` | Опц. (1–3 строки) | Проверяется в ретро |
| `kill_criteria` | Опц., для эксп. — обязательно | См. §3.4.4 |
| `parent_initiative_id` | Опц. | Если создана как продолжение (B') — ссылка на оригинал |
| `created_from_task_id` | Опц. | Fast path §3.8 |
| `status` | Авто | планируется / в работе / сделана / убита |
| `done_at` | Авто | Для архива и Сводки |

#### 3.4.2. Эксперимент-поля (для type = эксперимент)

| Поле | Назначение |
|---|---|
| `hypothesis` | «Если X, то Y увеличится на Z%, потому что …» |
| `success_criteria` | Что считаем успехом численно |
| `kill_criteria` | При каком результате убиваем |
| `sample_size_or_duration` | Выборка или срок |
| `result` | Заполняется при done |
| `decision` | `validated` / `invalidated` / `inconclusive` |

#### 3.4.3. RICE-поля (приоритизация)

| Поле | Шкала | Пример (Email-канал) |
|---|---|---|
| `rice_reach` | numeric, сколько затронуто (см. ниже) | 10 |
| `rice_impact` | `0.25` / `0.5` / `1` / `2` / `3` (Минимальный/Малый/Средний/Большой/Массивный) | 2 |
| `rice_confidence` | `0.5` / `0.8` / `1.0` (Низкая/Средняя/Высокая) | 0.8 |
| `rice_effort_hours` | = `estimate_hours` | 80 |
| `rice_score` | (Reach × Impact × Confidence) / (Effort / 40) | 8.0 |

**Расширенный расчёт reach** — суммирует:
- `linked_deal_ids.length` — сделки в pipeline, которые ждут инициативу.
- `linked_client_ids.length` — существующие клиенты (стадия договора и др.), на которых повлияет.

Пример: 3 сделки в pipeline ждут Email + 7 существующих клиентов в стадии договора оценят рассылки = reach 10.

PO может переопределить вручную, если нужно.

#### 3.4.4. Kill criteria

Для блокеров/зрелости — опц., для экспериментов — обязательно. В Сводке cron проверяет соответствие → алерт «соответствует своему kill criteria».

### 3.5. Зависимости между инициативами

Таблица `initiative_dependency_link`: `initiative_id`, `depends_on_initiative_id`. В Roadmap — стрелки. В раннем предупреждении — учёт цепочки.

### 3.6. Задача

**Физическая модель**: задача — это строка в существующей таблице `items` с `type='task'`. Отдельной таблицы `planning_tasks` нет; planning-поля (`initiative_id`, `linked_deal_id`, `planned_period_id`, `planned_date`, `why`, `replan_reason`, `is_carryover`) добавлены ALTER TABLE в `items`. Это позволяет переиспользовать существующий UI задач (мобильный, time-tracking, recurring-series, staging) без дублирования сущностей.

**Источник правды по содержимому**:
- `category = development` → Kaiten (двусторонняя синхронизация через `external_entity_links` + `sync_profiles`).
- `category ∈ {sales, account, support, legal}` → Second Brain.

**Категории** — фиксированный набор `{development, sales, account, support, legal}`. Реализуется как seed-записи в существующей таблице `categories` + soft-валидация в API (без CHECK constraint, чтобы не ломать существующие data).

| Поле | Обязательно | Зачем |
|---|---|---|
| `title` | Да | — |
| `why` | Да | Помнить, зачем |
| `initiative_id` | Опц. | Связь к метрике (если null → авто «Поддержка Qx») |
| `linked_deal_id` | Опц. | Для Sales/Account |
| `category` | Дефолт `development` | development / sales / account / support / legal |
| `estimated_minutes` | Опц. | Существующее поле `items` (с миграции 0007). Часы для capacity-расчёта получаем как `estimated_minutes / 60` |
| `planned_period_id` | Опц. | Неделя/месяц |
| `planned_date` | Опц. | Конкретный день (ПН-ВС). Задача целиком на день, не на часть дня. |
| `is_carryover` | Авто | TRUE если задача перенесена с предыдущего периода |
| `replan_reason` | При переплане | Категория из словаря |
| `status` | Авто | планируется / в работе / сделана |

**Связь с Kaiten-карточкой** — не отдельная колонка на `items`, а через существующую `external_entity_links` (provider='kaiten', local_entity_type='item'). Это единый источник правды (см. §17 и §6.7.5).

### 3.8. Создание инициативы из задачи

Кнопка «Сделать инициативой» на задаче → копируются title/description; в drawer выбираются `type`, `linked_metric_ids`, `due_period_id`, RICE; задача авто-привязывается.

### 3.9. Создание продолжения инициативы (B' из B)

При rescope/kill — кнопка «Создать продолжение». Копируются все поля исходной; PO правит:
- `title` += « (продолжение)»
- `due_period_id` — новая неделя
- `parent_initiative_id` — ссылка на оригинал

В Roadmap видна цепочка B → B'. В журнале — запись с привязкой.

## 5. Каскад, агрегация, приоритизация

- Top-down: фокус года → метрики → инициативы → задачи.
- Bottom-up: tick из источников → метрики; задачи done → % инициативы → матрица.
- RICE-сортировка в Колонках (по умолчанию дедлайн, тоггл RICE).
- Авто-архив `done` > 30 дней.

## 6. Двухслойное планирование

### 6.1. Стратегический слой (год / квартал)

Метрики + цели по горизонтам + инициативы с дедлайнами на неделю + RICE + допущения + kill criteria + зависимости.

### 6.2. Тактический слой (месяц / неделя)

Раскладка задач из инициатив по неделям и дням; capacity; поддерживающие задачи.

### 6.3. Поддерживающие задачи и авто-инициатива «Поддержка Qx»

В начале квартала система автоматически создаёт инициативу «Поддержка Qx 2026» (`type = поддержка`, `due_period_id = последняя неделя квартала`). Стихийные задачи (`initiative_id = null`) → авто-привязка к ней.

### 6.4. Ресурсное планирование (capacity в часах)

`capacity_hours_per_week` на разработчика, `estimate_hours` на задаче, `capacity_hours` на периоде. В UI — индикатор перегрузки.

### 6.5. Планирование задач по дням

На задаче — поле `planned_date` (конкретный день недели). **Без деления на утро/день/вечер** — задача ставится на день целиком.

В UI «Эта неделя» — grid из 5 дней (ПН–ПТ) + опционально СБ/ВС. Задачи перетаскиваются из sidebar в колонку дня. Задача может переехать на другой день целиком.

Перегрузка дня (сумма `estimate_hours` всех задач в дне > daily_capacity) — подсветка.

### 6.6. Соотношение стратегия / поддержка — целевая 70/30

Сводка считает: часы стратегических инициатив / часы «Поддержки». Целевое 70/30 (редактируется). Отклонение <60% или >80% — мягкое предупреждение.

### 6.7. Устранение ручника (автоматизации)

Восемь точек, где система автоматизирует рутину PO.

#### 6.7.1. Auto-distribute целей метрики по горизонтам

PO задаёт **только год**. Затем выбирает кривую распределения:
- **Линейная** — равномерно.
- **S-кривая** — медленный старт, ускорение, плато (типично для B2B SaaS).
- **Front-loaded** — большая часть в начале (для падающих метрик).
- **Back-loaded** — большая часть в конце.
- **По истории** — повторить распределение прошлого года ± дельта (доступно с второго года).
- **Custom** — заполнить вручную.

Система разносит цель по 4 кварталам / 12 месяцам / 52 неделям одной операцией. PO правит только аномалии (отпуск, конференция). Каждая ячейка остаётся inline-редактируемой.

UI: после выбора кривой — превью графика, кнопка «Применить». Затем toast «48 ячеек обновлено · Undo».

#### 6.7.2. Авто-ожидаемые рекуррентные платежи

Если сделка `stage = prod` и `min_monthly_amount > 0` и `production_started_at` задан — система **автоматически создаёт запись в `deal_payments` каждый месяц** на день, соответствующий дню `production_started_at`, со статусом `expected` и `amount = min_monthly_amount`.

PO **не подтверждает** — система автоматически считает эту запись фактом для метрики «Выручка». Если по факту платёж отличается — PO открывает запись и правит `amount`, статус становится `confirmed`.

**Если платёж не пришёл** — PO удаляет/обнуляет запись вручную; система пересчитывает Выручку.

Этот подход выбран как минимально-ручной: 90% случаев платежи приходят как ожидается, и PO ничего не делает.

#### 6.7.3. Smart suggestion привязки задачи к инициативе

**A. По keyword match.** При создании задачи (или синхронизации из Kaiten) система проверяет title/description против активных инициатив. Если есть совпадение ключевых слов — предлагает: «Похоже, эта задача относится к инициативе «Webhook reliability». Привязать?» Кнопки: «Да» / «Нет (в Поддержку)» / «Выбрать другую».

**B. Kaiten board ↔ Initiative mapping.** В `Settings → Kaiten boards mapping` — таблица соответствий «доска Kaiten → инициатива». Все задачи с доски «Email-канал» автоматически привязываются к инициативе «Email MVP». Mapping задаётся один раз.

#### 6.7.4. RICE auto-suggest

- **Reach** = `linked_deal_ids.length + linked_client_ids.length`. Переопределяется вручную.
- **Impact** — slider с подписями «Минимальный/Малый/Средний/Большой/Массивный» (значения 0.25/0.5/1/2/3 показаны мелким шрифтом).
- **Confidence** default = 0.8 (Средняя).
- **Effort** = `estimate_hours`, не отдельное поле.

Эффект: вместо 4 ввода — 1–2.

#### 6.7.5. Авто-fill stage timestamps

При `UPDATE deal SET stage = 'pilot'`:
- `pilot_started_at = NOW()` (если не задано).
- `pilot_planned_end_at = pilot_started_at + pilot_default_duration_days` (60 дней по умолчанию, настраивается в Settings, переопределяется на сделке).
- `stage_changed_at = NOW()`.

При `stage = production`: `production_started_at = NOW()`.

Cron daily: если `stage = pilot` и `pilot_planned_end_at < NOW()` — в Сводке: «Пилот ABC просрочен, нужно решить».

#### 6.7.6. Smart suggestion категории replan_reason + опциональность для мелких правок

**A. Smart suggestion.** Система видит, что изменилось:
- Сдвинут дедлайн инициативы → предложить `scope_underestimated` или `dependency_shifted`.
- Снижен target метрики → `priority_changed`.
- Срабатывание kill criteria → авто-проставляется `kill_criteria_triggered` без диалога.
- Добавлен emergent KR → `external_event`.

**B. Опциональность для мелких правок.** Изменение цели метрики на ≤5% от текущего значения — **не требует replan_reason**. Кладётся в журнал с `category = minor_adjustment` без диалога. Порог 5% — в `Settings → Минорные правки`.

Retrospective question всё ещё показывается, но как **опциональное поле** для минорных правок.

#### 6.7.7. Pre-fill квартальной ретроспективы из журнала

При открытии страницы квартальной ретроспективы система **анализирует журнал за квартал** и предлагает черновик:

- `what_went_well`: «Закрыто N инициатив в дедлайн: [список]. Выручка: X₽ vs план Y₽ ({+/-Z}%).»
- `what_didnt`: «Пропущено N дедлайнов: [список]. Метрика A не достигла цели.»
- `what_to_try`: пусто (PO заполняет — это про будущее).
- `lessons_learned`: «Эксперименты invalidated: …. Отработавшие kill criteria: ….»

PO редактирует draft. В 5 раз быстрее чистого листа.

#### 6.7.8. Spawn продолжения (B' из B)

На карточке инициативы с `status = killed` или `replan_reason.category ∈ {scope_underestimated, scope_overestimated}` — кнопка «Создать продолжение». Копирует все поля; PO правит `due_period_id` и `title`; ставится `parent_initiative_id`.

## 20. UX/UI стандарты

### 20.1. Принципы (что забираем у Linear / Notion / Sunsama)

#### Принцип 1. Inline editing — никаких модалок где не нужно

Клик на любое поле → редактирование на месте. Сохранение на blur / Enter. Никаких «Сохранить» кнопок.

- Таблица целей по горизонтам: клик на ячейку → input → Tab → следующая.
- Карточка инициативы: клик на title → редактирование; клик на due_period → dropdown.
- Только сложные многошаговые действия (создание новой инициативы с обязательными полями) — drawer справа, не модалка по центру.

#### Принцип 2. Optimistic UI — обновление мгновенно

Изменил поле → UI обновился сразу, sync в фоне. Если backend вернул ошибку → откат + toast «Изменения не сохранены».

Реализация: Zustand store → optimistic update → fetch → success: подтверждаем; error: rollback + toast.

#### Принцип 3. Progressive disclosure

На карточке инициативы:
- Свёрнуто: title, тип, статус, RICE-score, дедлайн.
- Раскрыто (по клику): + связанные метрики, сделки, описание.
- Полностью (открытая страница): + допущения, kill criteria, зависимости, эксп.-поля.

#### Принцип 4. Empty states с CTA

Метрика без целей → не пустая таблица:
```
У этой метрики ещё нет разбивки по горизонтам.

[Auto-distribute: Линейная]
[Auto-distribute: S-кривая]
[Auto-distribute: Back-loaded]
[Заполнить вручную]
```

#### Принцип 5. Цветовое кодирование статусов

Семантика (фиксирована):
- 🟢 Зелёный (`#16a34a`) — on-track, выполнено вовремя.
- 🟡 Жёлтый (`#eab308`) — at-risk, раннее предупреждение.
- 🔴 Красный (`#dc2626`) — off-track, пропустили.
- ⚪ Серый (`#9ca3af`) — будущее, не стартовано.
- 🔵 Синий (`#2563eb`) — в работе.
- ⚫ Тёмно-серый (`#374151`) — заархивировано / убито.

Применяется везде: бейджи, заливка карточек, точки в списках, акценты в Сводке.

### 20.2. Конкретные экраны

#### 20.2.4. Roadmap (SVAR Gantt)

Библиотека: **SVAR React Gantt** (MIT, open-source).

- Lanes по типам инициатив (Блокер / Зрелость / Тех. долг / Эксперимент / Поддержка) + lane «Sales/Account» из Second Brain.
- Полосы = инициативы от `created_at` до `due_period.end_date`.
- Цвет полосы по статусу (зелёный/жёлтый/красный/серый).
- Стрелки между полосами = зависимости (`initiative_dependency_link`).
- Drag-resize правого края полосы → меняется `due_period_id` (через replan flow с smart suggestion).
- Click на полосу → drawer с карточкой инициативы.
- Цепочка B → B' через `parent_initiative_id` показывается стрелкой особого стиля.

#### 20.2.6. Spreadsheet-режим (bulk-edit целей)

- Inline-edit ячеек (без keyboard navigation между ячейками).
- Tab/Enter на input → подтверждение значения; курсор остаётся в ячейке.
- Click на следующую ячейку — стандартная мышиная навигация.
- Bulk-update через **Re-distribute** (auto-distribute с кривой).
- Toast «N ячеек обновлено · Undo» после bulk-операций.

### 20.3. Микро-интеракции

- **Optimistic update animation** — поле меняется → лёгкая пульсация → подтверждение чёрной точкой → исчезает.
- **Drag-preview** при перетаскивании задачи — карточка следует за курсором с прозрачностью 70%.
- **Skeleton loaders** при загрузке — контурный layout, не spinner.
- **Subtle pulse** на «надо обратить внимание» — раннее предупреждение мягко мигает раз в 3 сек.
- **Toast с undo** — «N ячеек обновлено» / «Изменения отменены».
- **Smart copy-paste** в spreadsheet — копия из Excel/Google Sheets парсится корректно.

### 20.4. Производительность

Критично: PO будет работать с 200+ задачами, 6+ инициативами, 6+ месяцами истории. UI не должен лагать.

- **Виртуальные списки** (`react-window`) для списков >100 элементов (Бэклог задач Kaiten, журнал).
- **Pagination** в журнале (100 записей за раз, infinite scroll).
- **Memoize** Recharts-графиков (`React.memo` + `useMemo` для data props) — пересчёт только при изменении данных.
- **Suspense boundaries** для каждого блока Сводки — параллельная подгрузка, не блокирует весь экран.
- **Server components** где можно (Next.js 16 App Router).
- **Realtime через Supabase Realtime** — только для активного экрана, отписка при уходе.
- **Optimistic mutations** — UI не ждёт ответа сервера для inline-edit.
- **Debounce 300ms** на inline-edit перед отправкой PATCH.
- **Lazy-load Roadmap** — Gantt-компонент грузится только при заходе на /roadmap.

### 20.5. Библиотеки и зависимости

| Задача | Библиотека |
|---|---|

| Тосты | **sonner** |

| Состояние UI | **Zustand** (уже в стеке) |

### 20.6. Что НЕ делаем

- Keyboard shortcuts / Command palette ⌘K (отложено).
- Hover-preview карточек.
- Dark mode.
- AI-чат / LLM-копилот.
- Push-уведомления / алерты.
- Модалки для inline-действий.
- Wizard flows (кроме сложных bulk-импортов, которые тоже не делаем).
- Mobile-first вёрстка планировщика (это desktop-tool).
- Per-segment view.
- Time-blocking по утро/день/вечер.
- CSV-импорт платежей.

### 20.7. Темизация

- **Light mode только**. Background: `#ffffff` / `#f9fafb`.
- **Accent color** — настраиваемый в Settings (default `#2563eb`).
- Семантические цвета статусов (§20.1.5) — фиксированы, не темизируются.
- Шрифт — `Inter` (системный fallback `system-ui`).
- Радиусы — `4px` для inputs, `8px` для карточек, `12px` для drawer/modal.
- Тени — минимальные (Tailwind `shadow-sm`, `shadow`).
