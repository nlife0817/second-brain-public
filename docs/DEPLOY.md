# Автодеплой

Push в `v2-master` → GitHub гоняет тесты и сборку → если всё зелёное, ходит по SSH
на сервер и выкатывает ровно тот коммит. Заходить на сервер для обычного обновления
не нужно.

```
push в v2-master
      │
      ├─ npm ci → тесты → сборка (раннер GitHub, ~4 мин)
      │        ↳ упало — выкат не начинается, прод не тронут
      │
      └─ ssh root@сервер <sha>   (ключ прибит forced command к deploy.sh)
               │
               ├─ 1. git reset --hard <sha>
               ├─ 2. docker compose build app cron
               │        ↳ упало — откат кода, прежняя версия работает
               ├─ 3. migrate.sh: снимок базы + непринятые миграции
               │        ↳ упало — код не переключается
               ├─ 4. up -d --wait app  (ждёт healthcheck)
               ├─ 5. POST /api/v2/cron — проверка связки с базой, 3 попытки
               │        ↳ упало — возврат на образ :rollback
               └─ 6. чистка висячих слоёв и старого кеша сборки
```

Файлы: [.github/workflows/deploy.yml](../.github/workflows/deploy.yml),
[deploy/deploy.sh](../deploy/deploy.sh), [deploy/migrate.sh](../deploy/migrate.sh),
[deploy/cleanup.sh](../deploy/cleanup.sh).

## Разовая настройка

Порядок шагов важен: секреты в GitHub добавляются **последними**. Пока их нет,
выкат не состоится ни при каком push — а до шага 2 он и не должен состояться, иначе
попытается прогнать всю историю миграций поверх готовой базы.

### 1. Ключ для CI (на своём компьютере, PowerShell)

```powershell
ssh-keygen -t ed25519 -N '""' -C "github-actions-deploy" -f "$env:USERPROFILE\.ssh\sb_deploy_ci"
```

`-N '""'` — это не опечатка: PowerShell выбрасывает обычную пустую строку, и
`ssh-keygen` жалуется на нехватку аргумента.

Приватный ключ **не выводите на экран** — сразу в буфер обмена, оттуда в GitHub:

```powershell
Get-Content "$env:USERPROFILE\.ssh\sb_deploy_ci" -Raw | Set-Clipboard
```

Публичный ключ и отпечаток сервера показать можно, они не секретные:

```powershell
Get-Content "$env:USERPROFILE\.ssh\sb_deploy_ci.pub"; ssh-keyscan -t ed25519 203.0.113.10
```

### 2. Сервер (от root)

```bash
cd /srv/secondbrain && git remote set-branches origin '*' && git fetch --prune origin && git switch -C v2-master origin/v2-master && deploy/migrate.sh --dry-run
```

`--dry-run` покажет список файлов, которые скрипт считает непринятыми. Их там будет
много: учёт заводится с нуля, а схема давно накатана. Убедитесь, что в списке нет
ничего неожиданного — и отметьте всё применённым, **не выполняя**:

```bash
cd /srv/secondbrain && deploy/migrate.sh --baseline
```

Пропустить этот шаг нельзя: без него первый же выкат попытается прогнать всю историю
миграций поверх готовой базы.

Дальше — ключ CI. Он ограничен forced command: даже утёкший, он позволяет только
запустить выкат существующего коммита, но не выполнить произвольную команду и не
пробросить порт. Ваш собственный ключ это не затрагивает — ограничения в
`authorized_keys` действуют на ту строку, в которой записаны.

```bash
printf 'command="/srv/secondbrain/deploy/deploy.sh",restrict %s\n' 'ВСТАВЬТЕ_СЮДА_СОДЕРЖИМОЕ_sb_deploy_ci.pub' >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys && tail -2 ~/.ssh/authorized_keys
```

И еженедельная уборка в cron хоста:

```bash
( crontab -l 2>/dev/null; echo '40 4 * * 0 /srv/secondbrain/deploy/cleanup.sh >> /var/log/secondbrain-cleanup.log 2>&1' ) | crontab - && crontab -l
```

### 3. Секреты в GitHub

Только теперь — иначе выкат случится раньше, чем отмечена история миграций.
Settings → Secrets and variables → Actions → New repository secret:

| Имя | Значение |
|---|---|
| `DEPLOY_SSH_KEY` | приватный ключ целиком, из буфера обмена (вместе со строками `-----BEGIN…`/`-----END…`) |
| `DEPLOY_HOST` | `203.0.113.10` |
| `DEPLOY_KNOWN_HOSTS` | строка из `ssh-keyscan`, начинающаяся с этого же адреса |

Адрес в `DEPLOY_HOST` и адрес в `DEPLOY_KNOWN_HOSTS` обязаны совпадать посимвольно:
отпечаток, снятый для IP, к домену не подойдёт, и ssh откажется подключаться.

### 4. Проверка

Actions → «Прод» → Run workflow на ветке `v2-master`. Лог выката приходит прямо в
шаг «Выкат по SSH» — видно каждый шаг скрипта.

## Обычная работа

Ничего делать не нужно: слияние в `v2-master` = выкат. В логе Actions видно, что
именно уехало.

**Выкатить ветку вручную** — Actions → «Прод» → Run workflow, выбрать ветку в списке.

**Откатиться.** Если новая версия не поднялась, скрипт уже вернул прежний образ сам.
Если поднялась, но работает неправильно — `git revert <коммит>` и push: это обычный
выкат, он пройдёт тем же путём. С сервера то же самое делается напрямую:

```bash
/srv/secondbrain/deploy/deploy.sh <sha хорошего коммита>
```

## Миграции

Файлы `supabase/migrations/*.sql` применяются автоматически, по одному, каждый в
своей транзакции. Учёт — в `public._deploy_migrations` по имени файла; старая
`supabase_migrations.schema_migrations` осталась от Supabase и не используется.

Перед первой миграцией выката снимается дамп в `deploy/backups/pre-migrate-*.pgc`
(хранятся последние 10). **Откатить миграцию автоматически невозможно** — если
выкат упал после неё, схема останется новой.

Отсюда правило: **миграция должна быть совместима с текущим кодом**. Она
применяется до перезапуска приложения, то есть минуту-другую старый код работает с
новой схемой. Добавить колонку или таблицу — безопасно. Удалить или переименовать —
только следующим выкатом, после того как код перестал их использовать.

Два маркера в первых строках файла меняют поведение выката:

```sql
-- deploy: no-transaction   -- выполнить без единой транзакции (CREATE INDEX CONCURRENTLY)
-- deploy: manual           -- никогда не выполнять автоматически
```

`manual` — для необратимого: сноса таблиц, переливки данных, всего, что требует
проверки живыми глазами. Выкат такой файл пропускает и остаётся зелёным, а в логе
пишет, что файл ждёт. Запускают его отдельно, когда человек решил:

```bash
/srv/secondbrain/deploy/migrate.sh --run 0037_drop_v1_public.sql
```

`--baseline` ручные файлы **не** отмечает: иначе они числились бы применёнными,
ни разу не выполнившись.

Сейчас такая миграция одна — [0037_drop_v1_public.sql](../supabase/migrations/0037_drop_v1_public.sql),
снос таблиц первой версии. Она написана под Supabase и на нашем Postgres в текущем
виде упадёт: блок с `cron.unschedule` обращается к схеме `cron`, которой в контейнере
нет. Перед запуском его нужно убрать — подробности в шапке самого файла.

Следующий свободный номер — **0038**: номера 0034 и 0035 заняты дважды (в ветке
переезда и в `v2-master` они разные), 0036 и 0037 заняты в `v2-master`.

## Если выкат упал

Сообщение в логе Actions говорит, на каком шаге:

| Что в логе | Что случилось | Прод сейчас |
|---|---|---|
| падение до «Выкат на сервер» | тесты или сборка на раннере | не тронут |
| «сборка упала» | `docker compose build` на сервере | прежняя версия |
| «миграция не применилась» | ошибка в SQL | прежняя версия, схема не изменена |
| «вернул предыдущий образ» | новая версия не отвечала | прежняя версия, **схема уже новая** |
| «другой выкат ещё идёт» | два выката столкнулись | без изменений, повторите запуск |

Диагностика с сервера:

```bash
cd /srv/secondbrain/deploy && docker compose ps && docker compose logs --tail=100 app
```

## Чистка диска

Каждый выкат забирает висячие слои прежней сборки и кеш старше недели. Раз в неделю
`cleanup.sh` дочищает неиспользуемые образы и кеш. Тома не трогает никогда — в
`db-data` лежит база.

Посмотреть, сколько занято: `docker system df`. Убраться немедленно:
`/srv/secondbrain/deploy/cleanup.sh`.

Предыдущий образ хранится под тегом `secondbrain-app:rollback` — это цена
мгновенного отката, около 600 МБ. Если за неделю он не пригодился, еженедельная
уборка его унесёт.

## Вложения в описаниях задач

Файлы, вставленные в описание задачи, лежат в самой базе — `core.attachments.data`
(`bytea`). Своего объектного хранилища у нас нет, а том Docker не попадает в
`pg_dump`, которым снимается ежедневный бэкап: на диске рядом с базой файлы
пережили бы падение сервера только вместе с ним.

Цена решения — вес дампа. До этой возможности дамп был около 1 МБ и целиком
пересоздавался каждую ночь; теперь он растёт вместе с вложениями. Что держит рост
в рамках:

* файл ограничен 10 МБ (`ATTACHMENT_MAX_BYTES` в [attachments.ts](../src/lib/core/attachments.ts));
* картинка ужимается в браузере до отправки — не шире 1600 px, с перекодировкой в
  webp ([upload.ts](../src/components/v2/editor/upload.ts)). Снимок экрана на
  4 МБ приезжает в базу пятидесятикилобайтным;
* тик cron раз в 10 минут выносит вложения, которых больше нет в описании
  (`purgeOrphanAttachments`), с отсрочкой в сутки — чтобы не снести файл,
  загруженный в открытый редактор с несохранённым описанием.

Смотреть, сколько занято:

```bash
docker compose exec -T db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select count(*), pg_size_pretty(sum(byte_size)::bigint) from core.attachments;"
```

Когда это станет заметно (десятки гигабайт, ночной дамп по полчаса), правильный
следующий шаг — вынести байты в объектное хранилище S3, оставив в `core.attachments`
только метаданные и ключ. Роут отдачи файла и его проверки прав при этом не
меняются: снаружи адрес вложения остаётся прежним.

## Внешние календари

Календарь задач (`/v2/tasks`, вид «Календарь») работает без всякой настройки. Всё
ниже нужно только для того, чтобы рядом с задачами были видны встречи из внешних
календарей — и только для чтения: задачами они не становятся.

### Что добавить в `deploy/.env`

```bash
# Ровно 32 байта. Шифрует refresh-токен Google и приватную ссылку ICS-подписки.
openssl rand -hex 32
```

Значение кладётся в `CALENDAR_TOKEN_KEY`. Зачем шифровать в своей же базе:
содержимое `core` целиком уезжает в ночной дамп и лежит на диске две недели, а
refresh-токен даёт доступ к чужому календарю бессрочно и сам собой не
«переподписывается» — отозвать его можно только руками в аккаунте Google. Ключ
живёт в окружении, а не в базе: иначе дамп содержал бы и замок, и ключ.

Смена ключа означает, что подключения надо завести заново — экран настроек
покажет это прямым текстом («ключ CALENDAR_TOKEN_KEY изменился»). Сами события
восстановит первая же синхронизация; переподключить нужно только доступ.

### Что настроить в Google Cloud Console

Тому же OAuth-клиенту, через который работает вход:

1. включить **Google Calendar API** в проекте;
2. добавить на экран согласия скоуп `.../auth/calendar.readonly`;
3. добавить **второй** Authorized redirect URI —
   `https://<APP_DOMAIN>/auth/calendar/callback` (первый, `/auth/callback`,
   остаётся для входа). `redirect_uri` сверяется посимвольно.

Пока этого нет, вход работает как обычно, а подключение календаря возвращается с
ошибкой от Google — она видна на экране «Календари».

Согласие на календарь спрашивается **отдельно** от входа и с
`access_type=offline`: у входа скоуп узкий и refresh-токен ему не нужен, а
расширенное согласие на экране входа отпугивало бы тех, кому календарь не нужен.

### Как это живёт дальше

* Синхронизация — шаг тика cron (`syncDueCalendars`), подключение обновляется
  примерно раз в полчаса; кнопка «Обновить» в настройках делает то же немедленно.
* Синхронизируется скользящее окно: 120 дней назад и 400 вперёд (`SYNC_WINDOW` в
  [calendars.ts](../src/lib/core/calendars.ts)). Инкрементального `syncToken` у
  Google здесь нет — он несовместим с временным окном, а без окна выдача
  неограниченна.
* Сбой одного подключения остальных не задевает: причина садится в его
  `sync_error` и показывается в настройках. Отозванный в Google доступ выглядит
  именно так, а не «календарь просто перестал обновляться».
* ICS-подписка ходит только на внешние адреса: локальные и служебные диапазоны
  отсекаются (`isPrivateHost`), иначе подписка стала бы способом дёрнуть
  внутренний сервис или метаданные облака от имени приложения.

Посмотреть, что накопилось:

```bash
docker compose exec -T db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select a.provider, a.label, a.sync_error, count(e.id) from core.calendar_accounts a left join core.calendars c on c.account_id = a.id left join core.calendar_events e on e.calendar_id = c.id group by 1,2,3;"
```
