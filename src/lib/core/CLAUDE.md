# Ядро v2 (командный трекер)

Схема БД — `core` (Postgres). Наследие v1 в `public` удалено (миграция `0037_drop_v1_public.sql`); в `public` намеренно оставлены только два объекта v2 — функция `v2_cron_tick()` (тело расписания `v2_core_tick`) и `rls_auto_enable()` под EVENT TRIGGER `ensure_rls`. Дропать схему `public` целиком нельзя.

## Конвенции

- `uuid` первичные ключи, `timestamptz`/`date`/`time` — никаких TEXT-дат;
- каждая доменная таблица несёт `org_id`; композитные индексы начинаются с `org_id`;
- позиции — `double precision` (вставка между соседями без пересчёта);
- идентичность — `core.users.id`; вход резолвится по email (Google отдаёт только подтверждённый). Колонка `auth_user_id` осталась от Supabase Auth и больше не заполняется: она `uuid`, а Google выдаёт числовой `sub`;
- любая мутация пишет событие в `core.events`; уведомления раскладываются из событий в той же транзакции.

## Правила, которые легко нарушить

1. **Новая проверка прав — только в `policy.ts`** и с тестом в матрице. Проверка, размазанная по роутам, рано или поздно разойдётся с RLS.
2. **RLS — страховка, а не первый рубеж.** Приложение подключается к Postgres ролью-владельцем и политики обходит: реальные проверки живут в `policy.ts`. Политики остались на случай прямого доступа к базе (Realtime, ради которого они писались, после переезда на свой VPS нет); `auth.uid()` там теперь заглушка из `0034_selfhost_compat.sql`, возвращающая null, то есть режим deny-by-default. Меняя правило доступа в TypeScript, синхронно правь SQL-функции `core.can_view_project` / `core.can_view_task` / `core.user_can_view_*` — иначе слои разойдутся молча. Сделать RLS настоящим вторым рубежом можно только отдельной ролью коннекта с `FORCE ROW LEVEL SECURITY`.
3. **Доступ сотрудника к проекту решает сам проект** — колонка `core.projects.default_role` (миграция 0037): базовая роль, которую получает сотрудник организации без явной записи в `project_members`. `NULL` — закрытый проект: его видят ТОЛЬКО явные участники, включая org owner/admin (защита личного контура, а не недосмотр). Гость базовой ролью не пользуется никогда. `visibility` осталась производной generated-колонкой (`private` ⇔ `default_role is null`) для UI и экспорта — писать в неё нельзя, `INSERT`/`UPDATE` идут по `default_role`.
4. **Подписка (follower) не даёт доступа** к задаче, размещённой в проекте: иначе исключённый из проекта участник сохраняет доступ навсегда, самоподписавшись.
5. **`prepare()` из `lib/sql.ts` расплющивает массивы-аргументы** в позиционные параметры. Для `IN (...)` строй плейсхолдеры по длине массива и передавай массив одним аргументом. Оператор jsonb `?` в таких запросах писать нельзя — его съест конвертер `?`→`$N` (используй `jsonb_exists`). `undefined` в параметрах недопустим: нужен явный `null`, иначе `prepare()` бросит с номером параметра и текстом запроса (раньше это был безымянный `UNDEFINED_VALUE` от драйвера — по логу причину было не найти).
6. **jsonb — с обеих сторон не тип, а обещание.** На записи в `?::jsonb` передавай `JSON.stringify(...)`: двойное кодирование снимает `serializeJson` в [lib/sql.ts](../sql.ts) (штатный сериализатор postgres.js закодировал бы готовый JSON-текст ещё раз, и в колонке оказалась бы строка вместо массива — свой сериализатор из `types` не убирать). На чтении схема не проверяет ни форму записи, ни то, что там массив: класть такое прямо в параметры запроса нельзя, пропущенное поле уходит в драйвер как `undefined` и роняет транзакцию. Приводи форму — как `normalizeProjectGrants` для `invitations.project_grants`.
7. **Мутация без события — регресс.** Лента задачи, инбокс, push и вебхуки собираются из `core.events`; второй путь уведомлений заводить нельзя. Помни: `payload` события уходит наружу через вебхуки — не клади туда то, чего не должен увидеть подписчик.
8. **Выдача наружу требует фильтра видимости.** Экспорт, аудит, отчёты времени, поиск и вебхуки идут в обход обычных проверок проекта — каждый такой канал обязан отдельно фильтровать закрытые проекты, иначе он становится дверью в чужой контур.
9. **Отзыв доступа отзывает и следы.** Удаление участника (из проекта или организации) снимает назначения и подписки: без этого доступ сохраняется через `task_assignees`, а повторное приглашение воскрешает старые роли. Закрытие проекта (`default_role → null`) — исключение: исполнители его задач переносятся в явные участники (`preserveAssigneesOnClose`). Молча стирать назначения у половины организации нельзя, а «тихий» остаточный доступ через `task_assignees` — тем более: список участников снова описывает всех, кто видит проект, а лишних убирает админ.
10. **UI Base UI**: у `SelectValue` всегда передавай children, иначе в триггере отрисуется сырое значение (uuid). Утилиты вида `data-[side=right]:sm:max-w-sm` из обёрток бьют обычные классы по специфичности — переопределяй тем же вариантом.
11. **Даты и отметки времени приезжают из базы строками** — так объявлены типы, и код с ними обращается как со строками (`localeCompare`, `slice`, сравнение `<`). Держит это `PG_TYPES` в [lib/sql.ts](../sql.ts) — там же, где замена сериализатора jsonb. Новый временной тип (`timestamp`, `timetz`) нужно перечислять отдельным OID, иначе pg.js вернёт `Date`. Через JSON API подмена незаметна, а серверный рендер отдаёт результат выборки прямо в компонент — и падает на первой же сортировке.
12. **Состав экрана настроек настраивается, но только вниз.** `settings-sections.ts` держит и умолчания, и порог `minRole` каждого раздела; видимость — пересечение настройки владельца с этим порогом. Открыть роли раздел, данные которого ей не отдаст policy, нельзя: экран показал бы блок, который отвечает 403. Серверная страница обязана выбирать данные по тому же списку разделов — лишняя выборка это не только лишний запрос, но и 403 вместо экрана.
13. **Повтор задачи живёт в самой задаче** (`recurring_rules.task_id`, миграция 0038): шаблон новой задачи считается из живой строки в момент срабатывания. Копия не должна рождаться завершённой — статус вида `done`/`archived` заменяется первым рабочим, а задача без статуса копируется как есть. Старые правила со своим `template` (экран повторов удалён) продолжают материализоваться по-прежнему.
14. **Архивные задачи скрыты по умолчанию** (`showsArchived` в `views.ts`): «Архив = Показать» — переключатель видимости, а не предикат строки, поэтому `matchesGroups` его пропускает, а отсев идёт до фильтрации и группировки. Отсеивать архив после группировки нельзя — счётчики групп начнут врать.

## Производительность: что легко сломать обратно

1. **Списки не отдают `description`.** `TASK_LIST_COLUMNS` в `tasks.ts` перечисляет колонки явно; тип списка — `TaskListItem`, карточки — `TaskWithMeta`/`TaskDetail`. Возврат к `SELECT t.*` вернёт четверть веса ответа ради поля, которого нет ни на одной карточке.
2. **Проверка доступа — фиксированное число запросов.** Цепочка предков берётся одним рекурсивным CTE, проекты размещений — одним `IN`. Обход родителей циклом и `getProject` в цикле — это N+1 перед каждой мутацией задачи.
3. **Сессия проверяется локально** (`lib/auth/session.ts`, HMAC-SHA256 на WebCrypto, ключ импортируется один раз на уровне модуля). Сетевых вызовов на проверку сессии нет вообще. Реализация обязана оставаться Edge-совместимой: тот же код исполняет `proxy.ts`, где нет `node:crypto`.
4. **Корневой layout остаётся тонким.** В нём только шрифты, `ErrorBoundary`, `TooltipProvider` и регистрация service worker. Провайдер, тянущий за собой клиентскую подписку или тяжёлую библиотеку, попадёт на каждую страницу, включая `/login`.
5. **Тяжёлые библиотеки — через `next/dynamic`.** Tiptap (~370 КБ) грузится при первом открытии карточки. Статический импорт `RichText` вернёт его в бандл каждой страницы.
6. **Списки на сотни элементов рендерятся с пределом** (`CardList`, 50 + «показать ещё»). Каждая карточка доски — ещё и draggable: dnd-kit пересчитывает их на каждое движение мыши.
7. **Карточки мемоизированы, обработчик принимает id.** Инлайновая стрелка `onClick={() => open(t.id)}` создаётся заново на каждый рендер и сводит `memo` к нулю.
8. **Экран может отрендериться с пустыми справочниками** — при смене организации `metaLoading` поднимается заново. Там, где от `statuses`/`projects` зависит раскладка, нужен явный гейт.
9. **Контекст ячеек таблицы обязан быть стабильной ссылкой.** `patchTasks` читает строки из ref-зеркала, а не из состояния: иначе `cellCtx` пересоздаётся на каждое изменение списка и `memo` строк перестаёт работать — ровно та потеря, ради которой оно и вводилось.

## Загрузка экранов v2: серверный рендер

Холодная загрузка шла тремя последовательными волнами: `/me` (без него неизвестен `orgId`) → шесть справочников → данные страницы. Девять HTTP-запросов, и каждый заново поднимал сессию, членство и роли проектов — около 36 запросов к БД. Теперь всё считается за один серверный проход. Что легко сломать обратно:

1. **`page.tsx` каждого экрана — серверный компонент.** Он берёт контекст через `getActiveOrgAuth()` из `bootstrap.ts`, зовёт доменный слой напрямую и передаёт результат в `*Client.tsx` пропом `initial`. Возврат `"use client"` в `page.tsx` вернёт волну запросов после гидрации.
2. **Пользователь и контекст организации резолвятся один раз на запрос** — `cache()` из React в `context.ts` (`getCoreUser`, `getOrgAuth`) и в `bootstrap.ts`. Оболочка и страница рендерятся параллельно и оба их зовут; без мемоизации это две полные авторизации.
3. **Стор v2 — пер-запросный, через контекст** (`createV2Store` + `V2StoreProvider`). Модульный синглтон на сервере общий для всех одновременных запросов: наполнить его данными пользователя — утечка между организациями. Второе следствие: экраны читают стор прямо в рендере, поэтому на сервере он обязан быть наполнен, иначе разметка разойдётся с браузерной и React перерисует всё заново.
4. **Активная организация живёт в cookie** (`keys.ts`), а не в localStorage: сервер обязан знать, что рендерить, до первого скрипта. `switchOrg` пишет cookie и требует `router.refresh()` — иначе экран останется на данных прежней организации.
5. **Клиентский кэш GET — `lib/core/query.ts`.** Серверные данные садятся в него (`seed`) под тем же ключом, который построит `cachedGet`: совпал — запроса не будет вовсе. После мутации нужен `invalidate(prefix)`, иначе возврат на экран покажет состояние до правки. Ответы помечены поколением пути: запрос, начатый до мутации, в кэш уже не попадёт.
6. **Обновление по возврату в приложение и pull-to-refresh ходят мимо кэша** (`{ force: true }`). Смысл этих жестов — именно свежий ответ; отдать им закэшированный — вернуть ту жалобу, ради которой они появились.
7. **Ссылки сайдбара префетчат по наведению, а не при монтировании.** Экраны стали динамическими, и `prefetch` по умолчанию тянет маршрут без данных. `prefetch={true}` на всех ссылках сразу — десяток серверных рендеров на каждое открытие любого экрана.
8. **Глобальные слои монтируются с первого открытия** (`components/v2/lazy.tsx`). `next/dynamic` сам по себе не помогает: чанк тянется в момент рендера, а закрытый слой всё равно рендерится. Прямой импорт `TaskSheet`/`GlobalSearch`/диалогов вернёт их код в бандл каждой страницы.
9. **Сбой выборки роняет маршрут целиком.** Данные считаются на сервере, поэтому бросок из доменного слоя — это ошибка рендера, а не надпись в интерфейсе. Отказ по правам проверяй до выборок (`canOrg`), на остальное есть `app/v2/error.tsx`.

## Отклик на действие: регион, оптимизм, фоновый опрос

Загрузка экранов стала серверной, но действия оставались медленными: нажатие ждало правку на сервере и следом полный перечит списка. Замер на проде показал, что один поход в базу стоил ~700 мс — функции Vercel исполнялись в `iad1`, база живёт в `eu-central-1`. Что легко сломать обратно:

1. **`vercel.json` держит регион `fra1` — тот же город, что и база.** Это самая дорогая строка в репозитории: без неё каждый запрос к БД идёт через Атлантику (~95 мс на обращение), и роут с восемью последовательными запросами превращается в секунду ожидания на ровном месте. Переносить базу или регион — только вместе.
2. **Карточка задачи грузится одним запросом** — `/tasks/:id/bundle`. Было шесть (задача, комментарии, лента, подзадачи, связи, типы связей), и каждый заново разрешал пользователя, членство и роли проектов. Точечные роуты остались, но карточка ими не пользуется; `RelationsList` внутри карточки обязан получать `initialRelations`/`initialTypes`, иначе вернёт свои два запроса.
3. **Мутация не перечитывает список.** Ответ на правку — это уже новое состояние строки: карточка отдаёт его экрану через `TaskChange` (`lib/core/task-change.ts`), экран применяет `applyTaskChange` к своему списку. Полный перечит нужен только на `{ type: "reload" }` — когда задач стало больше.
4. **`TaskChange` приходит дважды: предсказание и подтверждение.** Побочную работу — обновление счётчиков сайдбара, `invalidate` кэша — вешать только на `confirmed: true`, иначе каждое действие уходит в сеть дважды.
5. **Оптимистичная правка обязана уметь откатываться.** Предыдущее состояние сохраняется до запроса и возвращается в `catch` вместе с повторным `onChanged`. Правка «на месте» без отката оставит интерфейс врущим после первой же ошибки сети.
6. **Предсказание повторяет правила сервера.** `previewPatch` в `TaskSheet` сам выводит `completed_at` по виду статуса — ровно как `updateTask`. Разойдутся правила — карточка мигнёт при получении ответа.
7. **Фоновый опрос молчит в скрытой вкладке** (`lib/core/use-poll.ts`). Счётчик непрочитанного и сверка таймера — это серверные функции с полной авторизацией; открытая фоном вкладка сутками занимала ими соединения к базе. При возврате во вкладку сверка идёт сразу, а не по следующему тику.

## v1 отключён

`proxy.ts` уводит адреса v1 в v2 (`legacyTarget`) и отвечает 410 на всё под `/api/`, кроме `/api/v2/`. Код v1 остался в репозитории и собирается — недоступен только через сеть.

Роуты, исключённые из `config.matcher`, проверку не проходят по построению: их дёргает pg_net без сессии. Cron-задачи v1 сначала выключили обратимо (`0034_disable_v1_cron.sql`), а после удаления самих роутов снимают совсем (`0037_drop_v1_public.sql`). Единственное живое расписание — `v2_core_tick`.

Публикация Realtime почищена — миграция `0035_drop_v1_from_realtime.sql`: из `supabase_realtime` убраны 39 таблиц схемы `public`, которыми v1 обновлял сетку через подписку. Семь таблиц схемы `core` оставлены как задел под живые обновления в v2; подписки на них пока нет ни одной.

**Это гигиена, а не производительность — не повторяй ошибку интерпретации.** Опрос WAL стоит первым в `pg_stat_statements` по `total_exec_time` (1.33 млн вызовов, 10 839 с), но счётчики копились 98 дней, а замер по коротким окнам до и после правки дал одно и то же: ~1.9 вызова в секунду и около одного процента одного ядра. Число таблиц в публикации на частоту опроса не влияет — служба Realtime дёргает слот по таймеру. Ранжирование `pg_stat_statements` по накопленной сумме показывает, что работало дольше всех, а не что грузит базу сейчас; для второго нужна дельта счётчиков по окну.

Живым из v1 остался `/api/mcp`: это внешняя интеграция, а не экран, и обрывать её заодно с интерфейсом было бы неожиданно.

## Таблица задач: сводный список и проект

`/v2/tasks` показывает задачи всех доступных проектов сразу; экран проекта (`/v2/projects/:id`, `/v2/m/projects/:id`) — те же строки в тех же колонках. Правила:

0. **Таблица со всей обвязкой — один компонент** `components/v2/tasks/TaskTableView`: шапка настроек, правка в строке, история (Ctrl+Z), выбор строк и массовые действия. Экран приносит только данные, ключ кэша и содержимое шапки. Данные и карточку задачи компонент себе не забирает: источники у экранов разные, а на телефоне к карточке прицеплен аппаратный «Назад» (`useBackDismiss`), которому в общем коде делать нечего.
1. **Фильтрация, сортировка и группировка — на клиенте.** Так реакция на настройку мгновенная, а счётчики групп честные: при серверной пагинации они врали бы. Плата — ответ ограничен `ALL_TASKS_CAP` и помечается `truncated`; молча обрезать нельзя.
2. **Видимость задач пакетно — только через `taskVisibility()` в `tasks.ts`.** `listAllTasks` и `filterVisibleTaskIds` строятся из одного источника; новый канал, которому нужен отсев задач, берёт `filterVisibleTaskIds`, а не пишет свой SQL. Разъехавшиеся копии этого правила — тот же класс ошибок, ради которого policy сделан единственным источником истины.
3. **Связь фильтрует «дальнюю» сторону сама** (`relations.ts`): задачи — по правам на задачу, клиенты — по доступу к CRM, проекты — по видимости проекта. Иначе список связей выдаёт названия чужих задач. Создание требует правку источника и доступ к цели: без второго связь становится способом проверить существование объекта по id.
4. **Настройки представления и карточки персистятся** (`view-store.ts`, localStorage). Набор и порядок колонок — рабочая привычка; терять её при перезагрузке нельзя. Ручная правка отвязывает от именованного представления, иначе «обновить» молча перезапишет сохранённое.
5. **Стор настроек — свой на каждую область** (`ViewScope`: `all` и `project:<id>`), раздаётся через `ViewStoreProvider`. Модульный синглтон здесь означал бы одну настройку на всё приложение: колонки, выставленные в проекте, перекраивали бы сводный список. У области `all` ключ в localStorage прежний (`sb.v2.tasksView`) — менять его нельзя, это чужие сохранённые представления. Кэш экземпляров живёт только в браузере: на сервере модульная карта общая для всех запросов.
6. **Экран проекта помнит вид** (`mode` в том же сторе): таблица или канбан-доска. Список задач принадлежит экрану, доска и таблица правят одни и те же строки — второй копии состояния быть не должно.
7. **Список проекта отдаёт `field_values`.** Колонки кастомных полей есть и в проекте; без значений они молча пустые на всех строках. Значения тянет общий `attachFieldValues` — одним запросом на список, а не по строке.
8. **Группы рисуют не больше `GROUP_PAGE` строк** и предлагают «показать ещё» — тот же предел, что у колонок доски.

## Push и фоновые задачи

Push-доставка — `lib/core/push.ts`: `after()` в `withOrg`/`withUser` вызывает диспетчер сразу после успешной мутации, поэтому пуш приходит мгновенно. Захват очереди атомарный (`FOR UPDATE SKIP LOCKED` + `dispatched_at` до отправки) — конкурирующие вызовы не дублируют. Подписки — `core.push_subscriptions` (`endpoint` уникален, поэтому перевыпуск подписки перепривязывает строку); диспетчер подставляет мобильный или десктопный URL по `user_agent` подписки.

`/api/v2/cron` (Bearer `CRON_SECRET`, исключён из `proxy.ts`) раз в 10 минут — страховка той же push-рассылки, плюс материализация повторяющихся правил, закрытие забытых таймеров, доставка вебхуков. Расписание ведёт контейнер `cron` (`deploy/cron/crontab`), секрет — из `deploy/.env`. Прежний путь через `pg_cron` + `pg_net` + Supabase Vault снят миграцией `0035_drop_supabase_cron.sql`.

## Мобильная версия и PWA

`/v2/m/*` — мобильные экраны с нижним таб-баром (`components/v2/mobile/MobileShell`); десктопный `/v2/layout.tsx` отдаёт этим путям детей без сайдбара, а его хуки (bootstrap, опрос непрочитанного) работают на обе оболочки. Карточка задачи — общий `TaskSheet` (на узких экранах он полноэкранный). Манифест мобильной оболочки — `/manifest-v2.webmanifest` (`start_url /v2/m/my`), задаётся серверным layout `/v2/m`; у корня свой `/manifest.webmanifest` (`start_url /v2/my`) для десктопной установки. Proxy уводит мобильные UA с десктопных экранов v2 на `/v2/m/*`; `?desktop` ставит сессионную cookie полной версии, `?mobile` снимает.

Что легко сломать обратной правкой:

1. **Событие установки ловит скрипт в разметке** (`mobile/install-capture.ts`), а не `useEffect`. Chrome присылает `beforeinstallprompt` до гидрации — слушатель в компоненте его не застаёт, и кнопка «Установить» не появляется вообще. Компоненты читают отложенное событие через `useInstallState`.
2. **Признаки окружения — через `useSyncExternalStore`** (`mobile/hooks.ts`: standalone, iOS, сеть, скрытые подсказки). `useState` + `useEffect` тут дают либо расхождение гидрации, либо нарушение `react-hooks/set-state-in-effect`.
3. **Слои закрываются аппаратной «Назад»** — `useBackDismiss` держит общий стек и ровно одну лишнюю запись в истории. Собственный `pushState` в компоненте рядом с этим хуком приведёт к тому, что «Назад» закроет чужой слой.
4. **Клик по уведомлению не перезагружает окно**: service worker шлёт `postMessage` открытой мобильной оболочке (`sw.js` → `openTarget`), и та переходит клиентской навигацией. `client.navigate()` остаётся только для десктопных окон.
5. **`data-mobile-v2` ставится на `<html>`**, а не на дерево оболочки: карточка задачи, диалоги и выпадающие списки рендерятся порталами в `body` — правила из `globals.css` (поля не мельче 16 px, иначе iOS зумит экран) иначе до них не достают.
6. **Экраны обновляются при возврате в приложение** (`useAppResume`) и жестом `PullToRefresh`. Фоновый таймер опроса в установленном приложении заморожен — без этого пользователь неделю смотрит на данные прошлого запуска. Исключение — экран проекта: таблица сама является областью прокрутки, а вложенный скроллер ломает жест (`PullToRefresh` считает, что список наверху, и срабатывает посреди страницы). Там вместо жеста кнопка обновления в шапке.
