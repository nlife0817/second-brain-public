# Ядро v2 (командный трекер)

Схема БД — `core` (Postgres), рядом с наследием v1 в `public`. Старые таблицы (`items`, `categories`, `users`, планирование, Kaiten) не трогаем: v1-интерфейс продолжает работать до полного переключения.

## Конвенции

- `uuid` первичные ключи, `timestamptz`/`date`/`time` — никаких TEXT-дат;
- каждая доменная таблица несёт `org_id`; композитные индексы начинаются с `org_id`;
- позиции — `double precision` (вставка между соседями без пересчёта);
- email — атрибут пользователя, идентичность — `core.users.id` ↔ `auth.users`;
- любая мутация пишет событие в `core.events`; уведомления раскладываются из событий в той же транзакции.

## Слои

| Файл | Ответственность |
|---|---|
| `policy.ts` | **Единственный** источник правил доступа. Чистые функции, покрыты `__tests__/policy.test.ts` |
| `context.ts` | `withOrg` / `withUser`: сессия → `core.users` → членство → `AuthContext` |
| `identity.ts` | Пользователи, организации, членство, приглашения |
| `projects.ts`, `tasks.ts`, `fields.ts`, `comments.ts`, `orgmeta.ts` | Домен задач |
| `clients.ts`, `time.ts`, `search.ts`, `recurring.ts` | CRM, учёт времени, поиск, повторы |
| `relations.ts` | Связи задача ↔ клиент ↔ проект (таблицы из миграции 0026) |
| `views.ts`, `view-store.ts` | Модель представлений сводного списка: фильтры, сортировка, группировка, колонки |
| `saas.ts`, `teams.ts` | Лимиты плана, вебхуки, аудит, экспорт, команды |
| `events.ts` | Событийная шина и уведомления |

Роуты в `src/app/api/v2/**` — тонкие: `parseJson` (zod) → `assertOrg`/`requireProject`/`requireTaskAccess` → сервис. SQL в роутах не пишем.

## Правила, которые легко нарушить

1. **Новая проверка прав — только в `policy.ts`** и с тестом в матрице. Проверка, размазанная по роутам, рано или поздно разойдётся с RLS.
2. **RLS — страховка, а не первый рубеж.** Приложение подключается к Postgres ролью-владельцем и политики обходит: реальные проверки живут в `policy.ts`. Политики нужны для Realtime и на случай прямого доступа к базе. Меняя правило доступа в TypeScript, синхронно правь SQL-функции `core.can_view_project` / `core.can_view_task` / `core.user_can_view_*` — иначе слои разойдутся молча. Сделать RLS настоящим вторым рубежом можно только отдельной ролью коннекта с `FORCE ROW LEVEL SECURITY`.
3. **Приватный проект видят только явные участники** — включая org owner/admin. Это защита личного контура, а не недосмотр.
4. **Подписка (follower) не даёт доступа** к задаче, размещённой в проекте: иначе исключённый из проекта участник сохраняет доступ навсегда, самоподписавшись.
5. **`prepare()` из `lib/sql.ts` расплющивает массивы-аргументы** в позиционные параметры. Для `IN (...)` строй плейсхолдеры по длине массива и передавай массив одним аргументом. Оператор jsonb `?` в таких запросах писать нельзя — его съест конвертер `?`→`$N` (используй `jsonb_exists`).
6. **Мутация без события — регресс.** Лента задачи, инбокс, push и вебхуки собираются из `core.events`; второй путь уведомлений заводить нельзя. Помни: `payload` события уходит наружу через вебхуки — не клади туда то, чего не должен увидеть подписчик.
7. **Выдача наружу требует фильтра видимости.** Экспорт, аудит, отчёты времени, поиск и вебхуки идут в обход обычных проверок проекта — каждый такой канал обязан отдельно фильтровать приватные проекты, иначе он становится дверью в чужой контур.
8. **Отзыв доступа отзывает и следы.** Удаление участника (из проекта или организации) снимает назначения и подписки: без этого доступ сохраняется через `task_assignees`, а повторное приглашение воскрешает старые роли.
7. **UI Base UI**: у `SelectValue` всегда передавай children, иначе в триггере отрисуется сырое значение (uuid). Утилиты вида `data-[side=right]:sm:max-w-sm` из обёрток бьют обычные классы по специфичности — переопределяй тем же вариантом.

## Производительность: что легко сломать обратно

1. **Списки не отдают `description`.** `TASK_LIST_COLUMNS` в `tasks.ts` перечисляет колонки явно; тип списка — `TaskListItem`, карточки — `TaskWithMeta`/`TaskDetail`. Возврат к `SELECT t.*` вернёт четверть веса ответа ради поля, которого нет ни на одной карточке.
2. **Проверка доступа — фиксированное число запросов.** Цепочка предков берётся одним рекурсивным CTE, проекты размещений — одним `IN`. Обход родителей циклом и `getProject` в цикле — это N+1 перед каждой мутацией задачи.
3. **Сессия проверяется локально** (`lib/supabase/claims.ts`, ES256 + кэш JWKS на уровне модуля). `auth.getUser()` — сетевой вызов на каждый запрос; он остаётся только фолбэком. Клиент Supabase создаётся заново на каждый запрос, поэтому кэш ключей обязан жить вне клиента.
4. **Обвязка v1 не монтируется на v2.** `LegacyRuntimeGate` в корневом layout: Realtime-подписка на `public`, тайм-трекинг и браузерный клиент Supabase (~220 КБ) нужны только экранам v1. Прямой импорт этих провайдеров в корневой layout вернёт их на все страницы.
5. **Тяжёлые библиотеки — через `next/dynamic`.** Tiptap (~370 КБ) грузится при первом открытии карточки. Статический импорт `RichText` вернёт его в бандл каждой страницы.
6. **Списки на сотни элементов рендерятся с пределом** (`CardList`, 50 + «показать ещё»). Каждая карточка доски — ещё и draggable: dnd-kit пересчитывает их на каждое движение мыши.
7. **Карточки мемоизированы, обработчик принимает id.** Инлайновая стрелка `onClick={() => open(t.id)}` создаётся заново на каждый рендер и сводит `memo` к нулю.
8. **Оболочка v2 не ждёт справочники** — `ready` выставляется сразу после `/me`. Значит, экран может отрендериться с пустыми `statuses`/`projects`: там, где от них зависит раскладка, нужен явный `metaLoading`-гейт.
9. **Контекст ячеек таблицы обязан быть стабильной ссылкой.** `patchTasks` читает строки из ref-зеркала, а не из состояния: иначе `cellCtx` пересоздаётся на каждое изменение списка и `memo` строк перестаёт работать — ровно та потеря, ради которой оно и вводилось.

## Сводный список «Все задачи»

`/v2/tasks` показывает задачи всех доступных проектов сразу. Правила:

1. **Фильтрация, сортировка и группировка — на клиенте.** Так реакция на настройку мгновенная, а счётчики групп честные: при серверной пагинации они врали бы. Плата — ответ ограничен `ALL_TASKS_CAP` и помечается `truncated`; молча обрезать нельзя.
2. **Видимость задач пакетно — только через `taskVisibility()` в `tasks.ts`.** `listAllTasks` и `filterVisibleTaskIds` строятся из одного источника; новый канал, которому нужен отсев задач, берёт `filterVisibleTaskIds`, а не пишет свой SQL. Разъехавшиеся копии этого правила — тот же класс ошибок, ради которого policy сделан единственным источником истины.
3. **Связь фильтрует «дальнюю» сторону сама** (`relations.ts`): задачи — по правам на задачу, клиенты — по доступу к CRM, проекты — по видимости проекта. Иначе список связей выдаёт названия чужих задач. Создание требует правку источника и доступ к цели: без второго связь становится способом проверить существование объекта по id.
4. **Настройки представления и карточки персистятся** (`view-store.ts`, localStorage). Набор и порядок колонок — рабочая привычка; терять её при перезагрузке нельзя. Ручная правка отвязывает от именованного представления, иначе «обновить» молча перезапишет сохранённое.
5. **Группы рисуют не больше `GROUP_PAGE` строк** и предлагают «показать ещё» — тот же предел, что у колонок доски.

## Push и фоновые задачи

Push-доставка — `lib/core/push.ts`: `after()` в `withOrg`/`withUser` вызывает диспетчер сразу после успешной мутации, поэтому пуш приходит мгновенно. Захват очереди атомарный (`FOR UPDATE SKIP LOCKED` + `dispatched_at` до отправки) — конкурирующие вызовы не дублируют. Подписки v2 — `core.push_subscriptions` (у core-пользователя может не быть строки в whitelist v1), диспетчер шлёт в объединение с `public.push_subscriptions` и подставляет мобильный/десктопный URL по user_agent подписки.

`/api/v2/cron` (Bearer `CRON_SECRET`, исключён из `proxy.ts`) раз в 10 минут — страховка той же push-рассылки, плюс материализация повторяющихся правил, закрытие забытых таймеров, доставка вебхуков. Расписание — `pg_cron` + `pg_net` (`supabase/migrations/0027_core_cron.sql`), секреты в Supabase Vault (`app_url`, `cron_secret`).

## Мобильная версия и PWA

`/v2/m/*` — мобильные экраны с нижним таб-баром (`components/v2/mobile/MobileShell`); десктопный `/v2/layout.tsx` отдаёт этим путям детей без сайдбара, а его хуки (bootstrap, опрос непрочитанного) работают на обе оболочки. Карточка задачи — общий `TaskSheet` (на узких экранах он полноэкранный). Манифест v2 — `/manifest-v2.webmanifest` (`start_url /v2/m/my`), задаётся серверным layout `/v2/m`; у корня остаётся манифест v1. Proxy уводит мобильные UA с десктопных экранов v2 на `/v2/m/*`; `?desktop` ставит сессионную cookie полной версии, `?mobile` снимает.
