# Режим «Разработка» для проекта — проработка

**Статус: шаги 1 и 2 реализованы** (миграции 0051 и 0052). Правила переехали в
[src/lib/core/CLAUDE.md](../src/lib/core/CLAUDE.md) — разделы «Режим проекта
„Разработка“» и правило 16г. Здесь остаётся история решений и то, что не
делалось: метрики спринта (шаг 3), бэклог на мобильной оболочке, `set_id not
null` со снятием триггера совместимости следующим выкатом.

Документ проектный: описывает, что и в каком порядке делать. Удалить его можно,
когда шаг 3 либо сделан, либо признан ненужным.

## Что решено

| Вопрос | Решение |
|---|---|
| Статусы dev-проекта | Наборы статусов: `core.status_sets`, проект выбирает набор |
| Единица планирования | Часы — существующее поле `estimated_minutes` |
| Ёмкость | Только общая на спринт; ёмкости по участникам не заводим |
| Сроки при переезде | Не двигаются молча — галочка в диалоге с умным дефолтом (см. §6.5) |
| Проверки перед стартом | Предупреждения, а не запреты |
| Сбор требований | Ничего специфичного не добавляем |
| Порядок | Шаг 1 — спринты и бэклог, шаг 2 — наборы статусов, шаг 3 — метрики |

## Идея в двух абзацах

У проекта появляется `mode`. В обычном режиме экран проекта работает как сейчас
(таблица, доска, гант, календарь). В режиме `dev` к ним добавляется вид
**«Бэклог»** — он же экран планирования: сверху сложены спринты, снизу
ранжированный бэклог, задачи перетаскиваются между ними. Доска в dev-режиме по
умолчанию показывает активный спринт, а не весь проект.

Второй слой — статусы. Сейчас справочник один на организацию; появляются
**наборы**, и проект выбирает свой. Категории (`backlog / in_progress / done /
archived`) остаются семантикой ядра — «Code review» и «QA» это `in_progress`, и
вся логика `completed_at`, скрытия архива и группировок продолжает работать без
правок.

## 1. Модель данных

### 1.1 Миграция 0051 — спринты и режим проекта

```sql
alter table core.projects
  add column mode text not null default 'standard'
    check (mode in ('standard', 'dev'));

create table core.sprints (
  id               uuid primary key default gen_random_uuid(),
  org_id           uuid not null references core.organizations(id) on delete cascade,
  project_id       uuid not null references core.projects(id) on delete cascade,
  name             text not null,
  goal             text not null default '',
  starts_on        date,
  ends_on          date,
  state            text not null default 'planned'
                     check (state in ('planned', 'active', 'completed')),
  -- Ёмкость в минутах — той же единицей, что tasks.estimated_minutes.
  capacity_minutes integer,
  position         double precision not null,
  started_at       timestamptz,
  completed_at     timestamptz,
  created_by       uuid references core.users(id) on delete set null,
  created_at       timestamptz not null default now()
);

-- Активный спринт в проекте ровно один — тем же приёмом, что is_default статуса.
create unique index sprints_one_active on core.sprints (project_id) where state = 'active';
create index sprints_project on core.sprints (org_id, project_id, position);

alter table core.tasks
  add column sprint_id uuid references core.sprints(id) on delete set null,
  -- Сколько раз задача не поместилась в завершаемый спринт. Растёт только на
  -- completeSprint: ручное перепланирование до старта переездом не считается.
  add column sprint_carry_count integer not null default 0;
create index tasks_sprint on core.tasks (org_id, sprint_id) where sprint_id is not null;
```

Почему `on delete set null` у `tasks.sprint_id`: удаление спринта не имеет права
уносить задачи — это ровно тот же принцип, что у `deleteProject`, который не
трогает задачи.

**Ранг бэклога отдельной колонкой не заводим.** Порядок задачи внутри проекта уже
есть — `core.task_projects.position` (double precision, `listProjectTasks` по ней
и сортирует, правит `moveTaskInProject`). Это и решение multi-homing: у задачи,
лежащей в двух проектах, два независимых ранга, по одному на проект.

### 1.2 Миграция 0052 — наборы статусов

```sql
create table core.status_sets (
  id         uuid primary key default gen_random_uuid(),
  org_id     uuid not null references core.organizations(id) on delete cascade,
  name       text not null,
  is_default boolean not null default false,
  created_at timestamptz not null default now()
);
create unique index status_sets_one_default on core.status_sets (org_id) where is_default;

alter table core.task_statuses
  add column set_id uuid references core.status_sets(id) on delete cascade;
alter table core.projects
  add column status_set_id uuid references core.status_sets(id) on delete set null;

-- Бэкфилл: каждой организации набор «Основной» со всеми её статусами.
insert into core.status_sets (org_id, name, is_default)
  select id, 'Основной', true from core.organizations;
update core.task_statuses s
   set set_id = (select id from core.status_sets ss where ss.org_id = s.org_id and ss.is_default);

-- Дефолт статуса становится уникальным в наборе, а не в организации (индекс
-- idx_core_task_statuses_default заведён миграцией 0041).
drop index if exists core.idx_core_task_statuses_default;
create unique index idx_core_task_statuses_default
  on core.task_statuses (set_id) where is_default;
```

**Совместимость на время выката.** Миграция применяется до перезапуска
приложения, минуту-другую живёт старый код:

* он вставляет статусы без `set_id` — их не увидит ни один экран. Лечится
  триггером `before insert`, который проставляет дефолтный набор организации,
  если `set_id` не задан. Триггер снимается следующим выкатом вместе с
  `set null → not null` (тот же приём, что с зеркалом `kind` в 0041);
* снятие старого уникального индекса ему не мешает: переназначение дефолта он и
  так делает двумя стейтментами, индекс там был страховкой.

`projects.status_set_id` остаётся nullable **навсегда**: `null` = «основной набор
организации». Обычные проекты не обязаны ничего выбирать, а `resolveStatusSetId`
подставляет дефолт.

## 2. Домен

### 2.1 Новый файл `src/lib/core/sprints.ts`

```ts
listSprints(ctx, projectId, opts?: { includeCompleted?: boolean }): Promise<SprintWithTotals[]>
createSprint(ctx, projectId, input): Promise<Sprint>
updateSprint(ctx, sprintId, patch): Promise<Sprint>
startSprint(ctx, sprintId): Promise<Sprint>
completeSprint(ctx, sprintId, opts: { carryTo: string | null }): Promise<Sprint>
deleteSprint(ctx, sprintId): Promise<void>
```

`SprintWithTotals` несёт `task_count`, `estimated_minutes` (сумма по задачам) и
`done_count` — экран планирования показывает «набрано / ёмкость» и не должен
считать это отдельным запросом на каждый спринт.

Правила:

1. **Спринт принадлежит проекту, задача — одному спринту.** Положить в спринт
   можно задачу, у которой этот проект есть в цепочке размещений
   (`chain_project_ids` — механизм уже есть у подзадач). Иначе спринт становится
   способом утащить чужую задачу в свой проект.
2. **Активный спринт один** — держит частичный индекс, `startSprint` проверяет до
   `UPDATE` и отвечает 422 с человеческим текстом, а не 23505.
3. **Завершение переносит незакрытые.** Задачи спринта, чей статус не категории
   `done`/`archived`, уходят по выбору: в следующий планируемый спринт
   (`carryTo`) или в бэклог (`sprint_id = null`). Экран спрашивает, что делать,
   и показывает число.
4. **Чистая часть — в `sprint-model.ts`**: какие переходы состояния разрешены,
   что показывать в шапке (осталось дней, набрано часов, доля закрытых). Тот же
   приём, что `status-model.ts` — правило одно, а зовут его и сервер, и экран.

### 2.3 Multi-homing: задача в двух проектах с разными наборами

Статус у задачи один, а наборов у её проектов может быть два. Значит **набор — это
то, что показываем, а не то, что запрещаем**:

* доска проекта рисует колонки своего набора **плюс** колонки для статусов,
  которые фактически встречаются у задач (`boardStatuses`). Молча спрятать
  задачу нельзя — она исчезнет из проекта, не будучи никуда перемещённой;
* ряд статусов в карточке (`cardStatuses`) — набор проекта задачи плюс её
  текущий статус, ровно как сейчас поступают с архивным;
* фильтр «Статус» в проекте предлагает статусы набора, но не режет остальные.

## 4. Права

Новых действий в `policy.ts` два, оба с тестом в матрице (правило 1 ядра):

* `sprint.manage` — уровень проекта, минимальная роль **editor**. Спринт это
  планирование работы, а не настройка проекта: сузить до admin означало бы, что
  команда не может передвинуть свою же задачу;
* `statuses.manage` уже есть (org, admin) — наборы попадают под него.

Переключение `mode` — `project.update` (admin проекта). Но новый набор статусов
при этом создаёт только org-admin: администратор проекта, не будучи админом
организации, выбирает набор из существующих. Экран это показывает явно, а не
отдаёт 403 на кнопку.

## 5. События и уведомления

* `sprint.created`, `sprint.started`, `sprint.completed` (в payload — сколько
  задач перенесено и куда). Лента проекта показывает их как вехи;
* перенос **одной** задачи в спринт — обычный `task.updated` со штатным событием:
  и в карточке, и перетаскиванием на экране планирования это один и тот же PATCH;
* массовый перенос при завершении спринта событий на задачи **не** пишет — одно
  событие на спринт. Это сознательное исключение из правила 7, как правка
  справочника статусов: иначе финиш спринта — это полсотни строк в ленте и push
  всей команде;
* новых типов уведомлений (`notification-kinds.ts`) в первом шаге не заводим.

## 6. Экраны

### 6.1 Вид «Бэклог» (он же планирование)

`ProjectViewMode` получает значение `backlog`; в dev-режиме переключатель видов
показывает **Бэклог · Доска · Таблица · Гант · Календарь**, в обычном — как
сейчас. Отдельного экрана планирования нет: сложенные спринты и бэклог на одной
странице и есть планирование.

* сверху — карточки спринтов: имя, даты, «набрано / ёмкость» в часах, полоса
  заполнения, кнопка «Начать» у планируемого и «Завершить» у активного;
* спринт разворачивается в список своих задач, задачи перетаскиваются между
  спринтами и бэклогом;
* снизу — бэклог: строки как в таблице (статус, исполнитель, оценка, теги),
  ручной порядок перетаскиванием, свёртка веток подзадач;
* плашка выделения — сколько часов выбрано и «В спринт» для массового переноса;
* **«Дозаполнить до ёмкости»** у планируемого спринта: берёт задачи из бэклога
  сверху, пока хватает остатка. Неоценённые пропускает и говорит, сколько
  пропустила, — иначе кнопка молча набивает спринт работой неизвестного объёма.

### 6.2 Доска в dev-режиме

Колонки — статусы набора. В шапке селектор: **Активный спринт** (по умолчанию) ·
Все задачи · Без спринта · конкретный спринт. Рядом — чип спринта: «Спринт 14 ·
осталось 4 дня · 28 из 40 ч».

### 6.3 Настройки проекта

Секция «Режим проекта»: переключатель `Обычный / Разработка` и выбор набора
статусов. При включении режима — предложение создать спринт, если ни одного нет.

### 6.4 Настройки организации

Экран статусов получает переключатель наборов (вкладки «Основной»,
«Разработка», «+ Набор»). Внутри вкладки — сегодняшняя раскладка по категориям с
перетаскиванием, инварианты 16а/16в применяются в границах набора.

### 6.5 Планирование, старт и переезд задач — правила

Самая живая часть режима: спринт планируют раз в две недели, а задачи переезжают
каждый день. Всё ниже — чистые правила, им место в `sprint-model.ts`, чтобы
диалоги и сервер считали одно и то же.

**Набор состава.** Четыре точки входа, все — один и тот же PATCH задачи:
перетаскивание на экране бэклога, поле «Спринт» в карточке, колонка и массовое
действие в таблице, меню карточки на доске. Пятая — «Дозаполнить до ёмкости»
(§6.1), она же массовый PATCH.

**Проверки перед стартом — предупреждения, не запреты.** Диалог «Начать спринт»
показывает итог и список того, что мешает; кнопка «Начать» активна всегда:

* задачи без оценки — «набрано 28 из 40 ч» врёт ровно на них;
* задачи без исполнителя;
* задача заблокирована задачей вне спринта — считается по существующим
  зависимостям `blocks` (`listTaskDependencies`, те же, что рисуют стрелки на
  ганте). Единственный пункт, который действительно ломает план;
* спринт перегружен относительно ёмкости.

Каждый пункт чинится прямо из диалога, а не «идите на другой экран».

**Сроки при переезде не двигаются молча.** `due_date` кормит гант, календарь и
напоминание исполнителю (`reminders.ts`), поэтому автоматический сдвиг на две
недели — это молча отменённая договорённость. Правило:

1. В диалоге переезда есть галочка «Сдвинуть сроки в новый спринт».
2. Она **включена по умолчанию**, если `due_date` попадал внутрь окна старого
   спринта: такая дата выглядит как план, а план и переезжает.
3. Она **выключена**, если дата вне окна (или спринта не было вовсе): это похоже
   на внешнее обязательство, и трогать его без спроса нельзя.
4. Сдвиг идёт **дельтой** `starts_on(новый) − starts_on(старый)`, а не «на конец
   спринта»: задача, стоявшая на третий день, останется на третьем. Если после
   сдвига дата вылезает за конец нового спринта (спринты разной длины) — она
   прижимается к его последнему дню. `start_date` едет той же дельтой.
5. При **выключенной** галочке диалог показывает конфликт красным: «Дедлайн
   12 авг. раньше конца Спринта 15 (31 авг.)».
6. Переезд из бэклога в спринт по умолчанию срок не ставит вовсе; галочка в этом
   случае означает «поставить срок на конец спринта».

**Завершение спринта — список, а не одна кнопка.** Диалог перечисляет незакрытые
задачи с умным дефолтом по категории статуса:

* задача начата (`in_progress`, в том числе Code review и QA) → в следующий
  спринт: прерывать идущую работу бессмысленно;
* задача не начата (`backlog`) → обратно в бэклог: она не поместилась, и её место
  в очереди должен решать приоритет, а не инерция.

Каждая строка перещёлкивается, внизу — «станет 32 из 40 ч в Спринте 15», чтобы
не переносить вслепую в уже полный спринт. Тем задачам, что уехали в другой
спринт, растёт `sprint_carry_count`; с двух переездов строка получает чип
«3-й спринт» — сигнал разбить, передать или выкинуть.

**Сдвиг самого спринта.** Смена `starts_on`/`ends_on` предлагает сдвинуть на ту
же дельту сроки задач, попадавших в старое окно, — тем же списком с галочками.
Правило то же, что при переезде задачи: даты вне окна не трогаем.

**След в истории.** Переезд одной задачи — штатное событие `task.updated`.
Массовый перенос при завершении — одно событие `sprint.completed` с числом
перенесённых: полсотни строк в ленте и пуш всей команде на финише спринта это
не отчёт, а шум.

## 7. Порядок работ

1. **Шаг 1 — спринты и бэклог.** Миграция 0050, `sprints.ts` + `sprint-model.ts`,
   роуты, `sprint_id` в задаче, вид «Бэклог», селектор спринта на доске,
   переключатель режима в настройках проекта. Самодостаточно и полезно сразу.
2. **Шаг 2 — наборы статусов.** Миграция 0052 с триггером совместимости, правки
   `orgmeta.ts`/`status-model.ts`, экран настроек, `boardStatuses` на доске.
   Следующим выкатом — `set_id not null` и снятие триггера.
3. **Шаг 3 — метрики спринта.** Burndown строится из `core.events` (история смен
   статуса уже пишется), отдельного хранилища снимков не нужно.

## 8. Риски и открытые места

1. **Наборы статусов трогают то, что уже трижды чинили** (0041, 0045, инварианты
   16–16в). Все три инварианта — «ровно один дефолт», «обязательные категории не
   пустеют», «позиции 1..N по категориям» — переезжают с организации на набор;
   тесты `status-model` расширяются набором, иначе регресс вылезет в проде
   выпадающим списком, где «Архив» стоит посреди работы.
2. **Спринт у подзадачи.** Подзадача — обычная задача, значит может иметь свой
   спринт. Вопрос к обсуждению: показывать ли в спринте подзадачу отдельной
   строкой, если её родитель в другом спринте (предлагаю показывать, с пометкой
   родителя, — иначе она пропадает из планирования).
3. **Гость.** `sprint.manage` от editor означает, что гость (project role
   `commenter`/`viewer`) спринты только видит. Отдельного запрета не нужно.
4. **Мобильная версия.** Вид «Бэклог» на телефоне — это список без drag&drop
   (перенос через меню строки «В спринт»). Планирование мышью на 375px не
   работает, и делать вид, что работает, не стоит.
